# ContentGuard for macOS

This directory holds the macOS side of ContentGuard: the same kind of
self-imposed, hard-to-disable content blocking the Android app
(`app/`) implements, extended to a Mac via fleet management, a native
on-device blocker, and app execution control.

## Build order

The macOS build is six phases, done strictly in order - each one depends on
state the previous phase left behind, and each has its own verification
checklist before moving on:

| Phase | What | Status |
|---|---|---|
| 0 | First-boot Mac setup: accounts, FileVault, Find My Mac, dev tools, WARP | done - accounts, Find My Mac, dev tools, Zero Trust/WARP all verified. FileVault and the admin account rename deliberately deferred; must land before Phase 5. |
| 1 | Fleet MDM on Fly.io, enrollment, `.mobileconfig` profiles | **done** - Fleet deployed, Mac enrolled and confirmed supervised, all 4 profiles pushed and verified (the 4th being Phase 2's PPPC profile, `profiles/pppc.mobileconfig` - pushed later than the other 3, once Phase 2 needed it), Fleet Premium purchased, Recovery Lock set and reboot-tested, all six verification tests passed, WARP switch locked, Gateway NSFW category block and DoH-provider IP blocklist both configured. FileVault, the admin account rename, and rotating the tunnel connector token are deliberately deferred to Phase 5's pre-lockdown checklist. |
| 2 | Native AI blocker: `ContentGuardAgent` (capture + NudeNet) + `ContentGuardDaemon` (tamper anchor) | **in progress** - real end-to-end detection **confirmed working live on the Mac**: real screen capture -> ONNX Runtime + CoreML inference on the real model -> correct confidence-threshold gating (a 0.0001-confidence blip correctly ignored, a genuine 0.83-confidence detection correctly triggered) -> `com.google.Chrome` actually force-terminated. The core of Phase 2 is proven end-to-end, not just built. Daemon also run live for the first time: correctly detected a missing agent heartbeat while a risky app was running and tried to fail closed, but `FallbackCover`'s lock mechanism was broken - it assumed `CGSession -suspend`, which Apple removed all the way back in Big Sur (2020) and was never actually run until now. Replaced with `pmset displaysleepnow`, and **confirmed working end-to-end on the real Mac**: display genuinely went to sleep and required the real login password to wake. "Require password immediately after sleep" in System Settings -> Lock Screen was already enabled, no setup gap after all. **Deliberate reaction change from the original spec**: on detection, the agent force-quits the frontmost app instead of covering the screen - no blackout, no daemon notification for this path. Chosen for disguise (a "crashed app" is much less suspicious/tempting-to-circumvent than an obvious block screen) over the cooldown protection the blackout approach gave; known and accepted tradeoff is that nothing stops immediately reopening the same app/site right after - no forced wait, no escalation on repeated triggers. The daemon's separate tamper-resistance (heartbeat monitoring, fail-closed if the agent goes quiet, escalation on repeated agent kills) is unchanged and still fully active - see `ContentGuardAgent/Sources/main.swift`'s `quitFrontmostApp()`. Also fixed a real SIGTRAP crash this surfaced: AppKit calls (`NSPanel`, `NSWorkspace`) were happening off the main thread from FrameProcessor's background queue - `OverlayManager.cover()/clear()` and `quitFrontmostApp()` both dispatch to main internally now. **Real launchd-managed install test completed, and it surfaced a genuine incident**: the agent's startup-failure paths still called `overlayManager.cover()` directly (a leftover from before the quit-frontmost-app reaction change above), and with `KeepAlive=true` plus a *persistent* startup failure (missing Screen Recording permission for the freshly-installed `/usr/local/bin/` path), that produced a real, confirmed lockout - a black screen surviving every restart, recovered live via ⌘+Space -> blind-typed Terminal -> `launchctl bootout` (the overlay's `.nonactivatingPanel` style mask doesn't steal keyboard focus, which is what made blind recovery possible at all). Fixed by removing both `overlayManager.cover()` calls from the agent's startup-failure paths entirely - the daemon's own heartbeat-based fail-closed (already proven escapable via `pmset displaysleepnow` + real password) is the backstop for that case now, not a second local cover mechanism with no matching `.clear()`. Once that was fixed, launchd-managed capture still failed with `SCStreamErrorDomain -3801` ("declined TCCs") on every `launchctl bootstrap`-triggered launch, while the identical signed binary worked fine launched directly from Terminal - chased at length (code signature match confirmed via `codesign` against the exact stored TCC requirement, `killall tccd`, toggling the Settings switch off/on, `tccutil reset`, a from-scratch re-sign with a fresh inode - none of it fixed the launchd-specific case) before landing on the real cause: this repo never actually had a PPPC profile pushed for Phase 2 (see Phase 1's row above), so every prior Screen Recording grant went through an ad-hoc interactive path (Settings toggle, a foreground Terminal launch) that doesn't reliably extend to a headless `launchd`-started background agent. Wrote and pushed `profiles/pppc.mobileconfig` (`Authorization: Allow`, not the signing test's `AllowStandardUserToSetSystemService` - that flag needs a live interactive click, which a headless LaunchAgent can never provide) and **confirmed working end-to-end on the real Mac**: repeated `launchctl bootout`/`bootstrap` cycles now capture and classify cleanly every time, `launchctl print` showing `state = running` with a live pid. Ran the real launchd verification checklist against that working install: **agent relaunch after kill confirmed** (`kill -9` -> `KeepAlive` brings a fresh pid back within seconds, no re-grant needed). **Fail-closed on agent trouble confirmed** (a kill-loop drove the agent through several rapid relaunches; the daemon genuinely locked the screen via `FallbackCover` - though it was `HeartbeatMonitor`'s heartbeat-grace check that won the race, not `EscalationManager`'s 5-kills/60s counter specifically, since `launchd`'s own relaunch throttling introduced a heartbeat gap first; the specific escalation-counter path is still unconfirmed in isolation). **Sleep/wake resume confirmed** (~36s real sleep, `CaptureManager.handleWake()`'s silent stream rebuild worked correctly, capture resumed with no manual relaunch). **Full-screen coverage surfaced a real, separate bug, now fixed**: testing detection during real macOS full-screen mode produced a string of near-zero-confidence classifications on content confirmed genuinely explicit, immediately followed by the `SCStream` silently dying entirely - capture stopped producing frames, but `HeartbeatClient.captureActive` (set once when `start()` succeeds, never re-evaluated - see that file) kept reporting healthy on every heartbeat, so the daemon's existing grace-window check never noticed: heartbeats were arriving exactly on schedule, they just contained a frozen frame count for 5+ minutes. Fixed the detection gap: `HeartbeatMonitor` now separately tracks `framesProcessed` staleness (`ContentGuardConfig.frameStallGraceSeconds`, 30s) alongside heartbeat-arrival staleness, and fails closed on either signal - a stalled-but-still-heartbeating agent now gets caught, and no longer incorrectly auto-clears an active fallback cover either (that logic used to trust any heartbeat arriving at all as proof of live capture). Isolated the root cause too: the same content reloaded in a normal windowed browser scored realistically (0.28, then a genuine 0.85-confidence detection that correctly force-terminated Chrome) rather than the near-zero scores seen in full-screen - confirming this was never a hard case for the classifier, full-screen mode itself was degrading what the classifier saw. Re-tested full-screen afterward and it worked cleanly the second time (real detection, real block, `SCStream` stayed healthy throughout) - so the original failure looks like a transient/non-deterministic `SCStream` hiccup rather than a reliable full-screen-specific break, which is exactly the kind of failure the new frame-stall detection exists to catch when it recurs, rather than something requiring a capture-side fix right now. **All four items of the real launchd verification checklist now pass**: relaunch after kill, fail-closed on agent trouble, sleep/wake resume, full-screen coverage. **`EscalationManager.classifyExit(pid:)` implemented for real and confirmed working on the real Mac**: it had been a permanent stub returning `.unknown` for every exit, since the daemon doesn't launch the agent (launchd does, per `LaunchAgents/com.contentguard.agent.plist`) so there's no parent-process `wait()` to observe a real exit status/signal through - fixed with a raw Darwin `kqueue`/`kevent()` watcher (`EVFILT_PROC`, `NOTE_EXIT`/`NOTE_EXITSTATUS`), the only way a non-parent-but-privileged process can get a PID's real wait-status on Darwin, decoding the POSIX wait-status bit layout by hand since the `WIFEXITED`/`WEXITSTATUS`/etc. C macros don't bridge into Swift. Verified live with two real signals sent to the running agent: `kill -9` correctly logged `agent exit observed: terminated(signal: 9)` (and counts toward the 5-kills/60s escalation threshold); `kill -SIGSEGV` correctly logged `agent exit observed: crash(signal: 11)` and did **not** trigger escalation - confirming the crash-vs-tampering distinction this whole file exists for actually holds up against a real signal, not just the design intent. Only remaining loose end from this stretch of testing: the frame-stall detection (`frameStallGraceSeconds`) hasn't yet been observed actually firing live (the full-screen retest that would have exercised it happened to stay healthy) - worth a deliberate test if a natural recurrence doesn't show up first. **A real `sudo reboot` test (not just launchd bootout/bootstrap cycles) surfaced a genuine boot-time race, now fixed**: right after login, the daemon locked the screen almost immediately, forcing a second login. Root cause: `HeartbeatMonitor`'s grace-window check has always treated "never received a heartbeat this daemon instance" as overdue immediately (deliberately, to close a real gap where a daemon restart mid-session with a risky app already open shouldn't get a free pass) - but at a real cold boot the daemon comes up well before login, and the instant a user logs in, macOS relaunches login items while `RunningAppCheck.isRiskyAppRunning()` counts any ordinary `/Applications` app (not just Chrome) as risky and the agent's ScreenCaptureKit stream is still spinning up - so the very next grace-check tick saw "no heartbeat yet" + "a login item is running" and failed closed within seconds of typing the password. Fixed with a one-time, bounded startup grace period (`ContentGuardConfig.agentStartupGraceSeconds`, 45s) timed from daemon start rather than from the last heartbeat - once elapsed, the original immediate-overdue behavior applies for the rest of that daemon instance's life, so this doesn't reopen an ongoing gap, just delays when the check starts being strict. Rebuild/redeploy since this fix has happened (see below), but the reboot itself hasn't been retested yet - worth doing once the app-lock verification below settles. **Added a new per-app lockout capability, closing the quit-frontmost-app tradeoff called out above**: `AppLockManager` (daemon-side, new) tracks how many times each app has been force-quit for a real detection, and once an app hits `appBlockCountThreshold` (4) it's locked out from relaunching for `appLockDurationSeconds` (10 minutes) - enforced by the daemon itself, polling the process table every 2s and killing any matching process directly (root, no dependency on the agent staying alive, same "only the daemon itself can end it" tamper-resistance philosophy as `BlackoutTimer`). The agent reports each detection-triggered quit over a new `appDetection` IPC message; `AppLockManager` independently refuses to ever track a `neverTerminateBundleIDs` entry regardless of what a message claims, as defense against the socket's existing user-writable trust model. **Deploying this surfaced a real process gap, not a code bug**: the Mac had silently been building from a commit several rounds old the entire time (a local, uncommitted Xcode-driven `project.pbxproj` edit was blocking every `git pull` from progressing, and `xcodebuild` doesn't care whether a pull succeeded - it just compiles whatever's on disk), so an initial "4 real detections, still no lockout" test result was against code that didn't contain the feature at all, not a confirmed bug. Once resolved (discard the stale local pbxproj edit, since the repo's own commit already carried an equivalent fix, then pull clean), the *first* genuine fresh build surfaced two real, previously-undiscovered issues of its own: a `heartbeatClient` reference inside `quitFrontmostApp()`'s closure needing explicit `self.` (this project sets `default-isolation=MainActor`, which changes closure-capture requirements the moment an instance member is actually referenced - fixed), and a stale `SWIFT_OBJC_BRIDGING_HEADER` build setting on the daemon target pointing at a bridging header file that has never existed anywhere in the repo (pure-Swift target, no Objective-C interop needed - setting removed). Also caught and fixed a real bug in the agent's own detection-report code along the way: `quitFrontmostApp()` was reading `NSRunningApplication.executableURL` *after* calling `forceTerminate()` on the same object, which silently produced no report at all - fixed by capturing it before termination, matching how `bundleID` was already safely captured. **Confirmed working end-to-end on the real Mac after all of the above**: a real 4-in-a-row detection test produced exactly `app detection recorded: com.google.Chrome (1/4)` through `(4/4)`, `com.google.Chrome hit 4 detections - locking it out for 600s`, and a relaunch attempt killed within 3 seconds (`tried to relaunch while locked out - killing pid ...`). |
| 3 | Santa app execution control | not started - **deliberately MONITOR/blocklist mode, not the original spec's LOCKDOWN** (see `profiles/README.md`'s note on `forceAdminPasswordForAppInstallation`) - standard users install freely, the Phase 2 content blocker is the real backstop against NSFW content regardless of app, and Santa's job narrows to denylisting specific known-bad tools (Tor Browser, etc.) rather than gatekeeping everything |
| 4 | Cloudflare Worker (ratchet, Santa sync, profile generation) + web dashboard | not started |
| 5 | Lockdown: demote to standard, seal admin credentials in the vault | not started |

Do not skip ahead. Phase 2's PPPC profile needs Phase 1's Fleet instance to
push it to; Phase 5's lockdown needs every earlier phase's verification
checklist to have actually passed, or you lock yourself out of a system
that doesn't yet do what it's supposed to.

## Why Phase 0 has no code

Phase 0 is entirely manual, hands-on-the-hardware steps - creating
accounts, toggling FileVault in System Settings, installing Xcode from the
App Store, pairing WARP to a Zero Trust org. None of it is scriptable from
here: this repo is being worked on from a sandboxed cloud environment with
no access to the physical Mac, its Apple ID, or the Cloudflare account it
enrolls into. `docs/PHASE_0_SETUP.md` is the runbook to follow by hand on
the Mac itself; `scripts/verify-phase0.sh` is a script to *run on that Mac*
afterward (copy it over, or `curl`/paste it) to check the parts of Phase 0
that are actually machine-verifiable before starting Phase 1.

Phases 1-5 do produce real code and configuration (Fleet deployment
config, `.mobileconfig` profiles, the `ContentGuardAgent`/`ContentGuardDaemon`
Swift sources, the Cloudflare Worker, the dashboard) - those land in this
directory, `profiles/`, and sibling `worker/`/`web/` directories as each
phase starts, once Phase 0 is verified complete on the actual hardware.

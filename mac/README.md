# ContentGuard for macOS

This directory holds the macOS side of ContentGuard: the same kind of
self-imposed, hard-to-disable content blocking the Android app
(`app/`) implements, extended to a Mac via fleet management, a native
on-device blocker, and app execution control.

## Build order

The macOS build is six phases, done strictly in order - each one depends on
state the previous phase left behind, and each has its own verification
checklist before moving on:

| Phase | What | Status |
|---|---|---|
| 0 | First-boot Mac setup: accounts, FileVault, Find My Mac, dev tools, WARP | done - accounts, Find My Mac, dev tools, Zero Trust/WARP all verified. FileVault and the admin account rename deliberately deferred; must land before Phase 5. |
| 1 | Fleet MDM on Fly.io, enrollment, `.mobileconfig` profiles | **done** - Fleet deployed, Mac enrolled and confirmed supervised, all 4 profiles pushed and verified (the 4th being Phase 2's PPPC profile, `profiles/pppc.mobileconfig` - pushed later than the other 3, once Phase 2 needed it), Fleet Premium purchased, Recovery Lock set and reboot-tested, all six verification tests passed, WARP switch locked, Gateway NSFW category block and DoH-provider IP blocklist both configured. FileVault, the admin account rename, and rotating the tunnel connector token are deliberately deferred to Phase 5's pre-lockdown checklist. |
| 2 | Native AI blocker: `ContentGuardAgent` (capture + NudeNet) + `ContentGuardDaemon` (tamper anchor) | **in progress** - real end-to-end detection **confirmed working live on the Mac**: real screen capture -> ONNX Runtime + CoreML inference on the real model -> correct confidence-threshold gating (a 0.0001-confidence blip correctly ignored, a genuine 0.83-confidence detection correctly triggered) -> `com.google.Chrome` actually force-terminated. The core of Phase 2 is proven end-to-end, not just built. Daemon also run live for the first time: correctly detected a missing agent heartbeat while a risky app was running and tried to fail closed, but `FallbackCover`'s lock mechanism was broken - it assumed `CGSession -suspend`, which Apple removed all the way back in Big Sur (2020) and was never actually run until now. Replaced with `pmset displaysleepnow`, and **confirmed working end-to-end on the real Mac**: display genuinely went to sleep and required the real login password to wake. "Require password immediately after sleep" in System Settings -> Lock Screen was already enabled, no setup gap after all. **Deliberate reaction change from the original spec**: on detection, the agent force-quits the frontmost app instead of covering the screen - no blackout, no daemon notification for this path. Chosen for disguise (a "crashed app" is much less suspicious/tempting-to-circumvent than an obvious block screen) over the cooldown protection the blackout approach gave; known and accepted tradeoff is that nothing stops immediately reopening the same app/site right after - no forced wait, no escalation on repeated triggers. The daemon's separate tamper-resistance (heartbeat monitoring, fail-closed if the agent goes quiet, escalation on repeated agent kills) is unchanged and still fully active - see `ContentGuardAgent/Sources/main.swift`'s `quitFrontmostApp()`. Also fixed a real SIGTRAP crash this surfaced: AppKit calls (`NSPanel`, `NSWorkspace`) were happening off the main thread from FrameProcessor's background queue - `OverlayManager.cover()/clear()` and `quitFrontmostApp()` both dispatch to main internally now. **Real launchd-managed install test completed, and it surfaced a genuine incident**: the agent's startup-failure paths still called `overlayManager.cover()` directly (a leftover from before the quit-frontmost-app reaction change above), and with `KeepAlive=true` plus a *persistent* startup failure (missing Screen Recording permission for the freshly-installed `/usr/local/bin/` path), that produced a real, confirmed lockout - a black screen surviving every restart, recovered live via ⌘+Space -> blind-typed Terminal -> `launchctl bootout` (the overlay's `.nonactivatingPanel` style mask doesn't steal keyboard focus, which is what made blind recovery possible at all). Fixed by removing both `overlayManager.cover()` calls from the agent's startup-failure paths entirely - the daemon's own heartbeat-based fail-closed (already proven escapable via `pmset displaysleepnow` + real password) is the backstop for that case now, not a second local cover mechanism with no matching `.clear()`. Once that was fixed, launchd-managed capture still failed with `SCStreamErrorDomain -3801` ("declined TCCs") on every `launchctl bootstrap`-triggered launch, while the identical signed binary worked fine launched directly from Terminal - chased at length (code signature match confirmed via `codesign` against the exact stored TCC requirement, `killall tccd`, toggling the Settings switch off/on, `tccutil reset`, a from-scratch re-sign with a fresh inode - none of it fixed the launchd-specific case) before landing on the real cause: this repo never actually had a PPPC profile pushed for Phase 2 (see Phase 1's row above), so every prior Screen Recording grant went through an ad-hoc interactive path (Settings toggle, a foreground Terminal launch) that doesn't reliably extend to a headless `launchd`-started background agent. Wrote and pushed `profiles/pppc.mobileconfig` (`Authorization: Allow`, not the signing test's `AllowStandardUserToSetSystemService` - that flag needs a live interactive click, which a headless LaunchAgent can never provide) and **confirmed working end-to-end on the real Mac**: repeated `launchctl bootout`/`bootstrap` cycles now capture and classify cleanly every time, `launchctl print` showing `state = running` with a live pid. Ran the real launchd verification checklist against that working install: **agent relaunch after kill confirmed** (`kill -9` -> `KeepAlive` brings a fresh pid back within seconds, no re-grant needed). **Fail-closed on agent trouble confirmed** (a kill-loop drove the agent through several rapid relaunches; the daemon genuinely locked the screen via `FallbackCover` - though it was `HeartbeatMonitor`'s heartbeat-grace check that won the race, not `EscalationManager`'s 5-kills/60s counter specifically, since `launchd`'s own relaunch throttling introduced a heartbeat gap first; the specific escalation-counter path is still unconfirmed in isolation). **Sleep/wake resume confirmed** (~36s real sleep, `CaptureManager.handleWake()`'s silent stream rebuild worked correctly, capture resumed with no manual relaunch). **Full-screen coverage surfaced a real, separate bug, now fixed**: testing detection during real macOS full-screen mode produced a string of near-zero-confidence classifications on content confirmed genuinely explicit, immediately followed by the `SCStream` silently dying entirely - capture stopped producing frames, but `HeartbeatClient.captureActive` (set once when `start()` succeeds, never re-evaluated - see that file) kept reporting healthy on every heartbeat, so the daemon's existing grace-window check never noticed: heartbeats were arriving exactly on schedule, they just contained a frozen frame count for 5+ minutes. Root cause traced, not yet fixed on the capture side (full-screen-specific `SCStream` death vs. general classifier accuracy on that content is still an open question - the windowed-mode comparison to isolate it hasn't been run yet), but the *detection gap* is fixed: `HeartbeatMonitor` now separately tracks `framesProcessed` staleness (`ContentGuardConfig.frameStallGraceSeconds`, 30s) alongside heartbeat-arrival staleness, and fails closed on either signal - a stalled-but-still-heartbeating agent now gets caught, and no longer incorrectly auto-clears an active fallback cover either (that logic used to trust any heartbeat arriving at all as proof of live capture). Still open: verify `EscalationManager.classifyExit(pid:)`'s exit-status mechanism for real; isolate whether full-screen mode itself breaks `SCStream` or whether the low confidence scores were just hard content for the classifier (rerun the same content windowed, and confirm a real detection force-quits a full-screen app specifically); confirm the new frame-stall detection actually fires on the real Mac (hasn't been tested live yet, only reasoned through against the actual incident's log data) |
| 3 | Santa app execution control | not started - **deliberately MONITOR/blocklist mode, not the original spec's LOCKDOWN** (see `profiles/README.md`'s note on `forceAdminPasswordForAppInstallation`) - standard users install freely, the Phase 2 content blocker is the real backstop against NSFW content regardless of app, and Santa's job narrows to denylisting specific known-bad tools (Tor Browser, etc.) rather than gatekeeping everything |
| 4 | Cloudflare Worker (ratchet, Santa sync, profile generation) + web dashboard | not started |
| 5 | Lockdown: demote to standard, seal admin credentials in the vault | not started |

Do not skip ahead. Phase 2's PPPC profile needs Phase 1's Fleet instance to
push it to; Phase 5's lockdown needs every earlier phase's verification
checklist to have actually passed, or you lock yourself out of a system
that doesn't yet do what it's supposed to.

## Why Phase 0 has no code

Phase 0 is entirely manual, hands-on-the-hardware steps - creating
accounts, toggling FileVault in System Settings, installing Xcode from the
App Store, pairing WARP to a Zero Trust org. None of it is scriptable from
here: this repo is being worked on from a sandboxed cloud environment with
no access to the physical Mac, its Apple ID, or the Cloudflare account it
enrolls into. `docs/PHASE_0_SETUP.md` is the runbook to follow by hand on
the Mac itself; `scripts/verify-phase0.sh` is a script to *run on that Mac*
afterward (copy it over, or `curl`/paste it) to check the parts of Phase 0
that are actually machine-verifiable before starting Phase 1.

Phases 1-5 do produce real code and configuration (Fleet deployment
config, `.mobileconfig` profiles, the `ContentGuardAgent`/`ContentGuardDaemon`
Swift sources, the Cloudflare Worker, the dashboard) - those land in this
directory, `profiles/`, and sibling `worker/`/`web/` directories as each
phase starts, once Phase 0 is verified complete on the actual hardware.

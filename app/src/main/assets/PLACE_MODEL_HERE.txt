NsfwClassifierFactory looks for 320n.onnx first, then nsfw.onnx,
then nsfw.tflite, then falls back to StubNsfwClassifier (always scores 0,
never blocks) if none are present.

As of this commit, 320n.onnx is the live gate-7 model (notAI-tech/NudeNet
v3's 320n export, FP32, run via NudeNetDetector.kt with the XNNPACK
execution provider). Unlike the earlier whole-image classifiers, this is a
body-part detector - exposed vs. covered is encoded in its label set
directly (see NudeNetGatePolicy in NudeNetDetector.kt for exactly which
labels gate blocking and their thresholds), which is what lets it tell
"gym clothes" apart from real nudity instead of relying on a single tuned
scalar. See SETUP.md section 5 for the full story.

nsfw.onnx (AdamCodd/vit-base-nsfw-detector, model_fp16.onnx variant - see
OnnxNsfwClassifier.kt) is a plain 2-class sfw/nsfw model with no "sexy"
distinction. OnnxNsfwClassifier still reads it if you drop it in here, but
it is deliberately NOT committed to this repo any more:

  - At 164MB it dwarfed the 12MB model actually in use, and Git LFS
    bandwidth is an exhaustible budget. Two CI checkouts per push meant
    ~352MB of LFS traffic per commit, which exhausted the repo's LFS
    budget outright - at which point `actions/checkout` fails and nothing
    builds at all. It also added 164MB to every APK.
  - As a fallback it bought almost nothing. It runs on the *same* ONNX
    Runtime as 320n.onnx, so any native/ORT failure takes out both
    identically; the only case it covered was "320n.onnx specifically is
    missing or corrupt while ORT is fine" - i.e. exactly the LFS-pointer
    scenario its own size was causing.
  - It is also superseded, not equivalent: a whole-image 2-class score
    with none of NudeNet's body-part label set, which is what lets gate 7
    tell gym clothes from real nudity (see NudeNetDetector's class doc).

If 320n.onnx ever does fail to load, that is now loud rather than a silent
swap to different detection semantics - NsfwClassifierFactory logs
CLASSIFIER_LOAD_FAILED and NO_CLASSIFIER to the Activity tab's Debug log.

--- Legacy TFLite path (nsfw.tflite) ---

Expected contract (see detect/TFLiteNsfwClassifier.kt):
  - Single image input, any HxW in the 128-160px range, NHWC layout.
  - Either float32 (normalized 0..1) or fully-integer-quantized
    (uint8/int8 with the standard TFLite scale/zero-point metadata) input.
  - Single-value output tensor: one NSFW probability in [0,1] (float32
    output, or quantized uint8/int8 dequantized via scale/zero-point).

TFLiteNsfwClassifier reads input size and dtypes off the model itself, so
as long as the shapes/types above hold, no code changes are needed beyond
dropping the file here. NsfwClassifierFactory falls back to
StubNsfwClassifier (always scores 0, never blocks) whenever this file is
absent - which is the state this repo ships in.

This file itself (PLACE_MODEL_HERE.txt) is harmless to leave in the APK;
delete it once nsfw.tflite is in place if you'd like.

Recommended source model: GantMan/nsfw_model (MIT licensed), MobileNetV2
variant - https://github.com/GantMan/nsfw_model. It's a 5-class softmax
(drawings/hentai/neutral/porn/sexy), not a single sigmoid, but
TFLiteNsfwClassifier already handles that (see its unsafeClassIndices
param - defaults to summing hentai+porn+sexy). See tools/convert_nsfw_model.py
for the exact conversion/quantization script and preprocessing details.
